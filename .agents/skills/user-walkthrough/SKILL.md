# 真人操作走查（user-walkthrough）

> **為什麼有這份 skill**：源專案曾經連續多張票在 `run-checks` 全綠、單元測試全過之後，
> 一交到案主手上就被打回——按鈕按了沒反應、功能存在但找不到入口、
> 訊息收到了畫面卻永遠顯示「傳送中」、指定密碼後行為與拍板相反。
> 共同根因：**測試驗的是零件，案主用的是過程。** 每個零件都對，組起來的體驗卻是壞的。
> 這份 skill 把「案主會做的事」變成出貨前的固定關卡。

## 何時用（強制）

任何票只要改動**使用者看得到或按得到**的東西——畫面、按鈕、表單、訊息、狀態顯示、
流程順序——在 `run-checks` 綠燈之後、**回報案主之前**，必須走完本清單。
純後端重構、純文件、純 CI 改動可跳過，但要在回報裡說明為什麼跳過。

## 核心原則：測過程，不是測零件

案主的一次操作是一條**時間線**：
`看到入口 → 按下去 → 等待 → 看到結果 → （狀態隨時間改變）→ 確認完成`。
單元測試往往只驗其中一格。走查的責任是把整條線走完，**每一步都看實際結果**。

歷史教訓對照（每一條都在源專案真的發生過）：

| 只驗了 | 漏掉的下一層 | 事故 |
|---|---|---|
| 檔案裡有那段字 | 頁面根本沒 render | 模板註解整段印在畫面上 |
| 按鈕有渲染出來 | 沒有真的按下去 | 對話框元件吞掉了按鈕的動作，按了沒反應 |
| 按下去有導頁 | 沒走完那一頁看結果 | 指定密碼繞過服務層，該清的旗標沒清 |
| 每個零件的狀態都對 | 沒走過時間線 | 輪詢只新增不更新，「傳送中」永遠卡住 |
| 斷言通過 | 斷言**永遠**會通過 | 對空資料庫斷言「沒有壞資料」 |

## 走查清單

### A. 入口（找得到嗎）

- [ ] **不知道功能在哪的人找得到嗎？** 從案主平常停留的頁面出發，不靠網址、不靠記憶。
      藏在列表頁「動作」下拉選單的功能等於不存在（上表「指定密碼」那次事故的起點）。
- [ ] 手機也找得到嗎？觸控裝置沒有 hover——只靠滑鼠移入出現的入口，手機上永遠按不到。
- [ ] 反向：**不該看到的人真的看不到？直接打網址也進不去？**
      藏按鈕擋不住 POST：權限一定在伺服器端檢查，用 Postman 直接呼叫 API 驗證。

### B. 操作（按下去有反應嗎）

- [ ] **真的按下去**，不是看按鈕存在。按了要在畫面上看得到後果。
- [ ] 按下去到有回饋之間**有沒有空窗**？超過一秒的無回饋會被當成「沒按到」而重按
      （所以要先顯示「送出中」這類中間狀態）。
- [ ] 重複按會怎樣？送出中有沒有鎖住？
- [ ] 失敗會怎樣？**要看得到失敗與原因**，不能畫面上與成功一模一樣
      （靜默消失、看不出傳送失敗，都發生過）。

### C. 時間線（等一下之後對嗎）

- [ ] 任何**會隨時間改變的狀態**（傳送中、處理中、載入中……），要走完整條線：
      觸發 → 中間態出現 → 完成 → **中間態消失**。最後一步最常漏。
- [ ] 畫面是輪詢／增量更新的話：**已經畫上去的東西之後還更新得到嗎？**
      只會新增、不會更新的機制，裝不下會變的狀態（「傳送中」卡住的根因）。
- [ ] 背景工作（排程、webhook）完成後，畫面多久反映？案主會等到嗎？

### D. 資料邊界（舊資料、別人的資料）

- [ ] **新欄位遇上舊資料**：既有資料在新功能下長什麼樣？
      （舊資料沒有新欄位的值、歷史資料全部顯示成中間狀態——後者要回填。）
- [ ] 空狀態：沒有資料時畫面說什麼？
- [ ] 中文與特殊字元真的能用嗎？測試用的資料庫和正式的資料庫行為可能不同
      （曾經出現搜尋只在測試環境通過的假綠燈）——懷疑時兩邊都跑。

### E. 一致性（畫面各處說法一樣嗎）

- [ ] 同一件事在不同位置的顯示**一致嗎**？徽章紅了、數字也要算到
      （徽章與頁籤兩套定義各說各話，同類問題發生過好幾次）。
- [ ] 同一個判斷只能有一份實作——散在前後端兩邊遲早走鐘。

### F. 對照拍板（行為跟案主要的一樣嗎）

- [ ] 回頭讀票的「需求細節」，逐條對照實際行為——尤其是**否定句**
      （「不強制」「不顯示」「不重複」）。曾經把「不強制改密碼」實作成
      「不設旗標」而不是「清旗標」，行為與拍板相反。
- [ ] 驗收標準裡凡是寫「案主實機驗證」的項目，**明確列給案主**，不要混在「已完成」裡。

## 測試的品質門檻（走查發現問題後補測試時）

1. **測試要能證明自己會紅**：寫完後把程式碼弄壞一次，確認對應測試真的變紅，再還原。
   反向驗證沒紅的測試等於沒寫（每張票的實作紀錄都要寫結果）。
2. **警惕永真斷言**：對空資料庫斷言「沒有壞資料」永遠會過。要自己造出「壞的前提」，
   再驗證修法把它變好。
3. **斷言要具體**：只斷言「丟出錯誤」，連打錯字的錯誤都算過；
   比對中文標籤可能命中說明文字而非按鈕（用按鈕的網址或角色斷言才準）。
4. **時間線用測試固定下來**：模擬「操作 → 輪詢 → 背景完成 → 再輪詢」的完整序列。
   注意測試環境常把背景工作改成立刻完成，會把中間態壓縮掉——必要時繞過端點、
   自己控制背景工作的時機。

## 回報格式

走查完，回報案主時分成兩欄，**不要混在一起**：

- **我驗過的**：走了哪條路徑、每步看到什麼。
- **只有你實機才驗得到的**：列成清單（例：通訊軟體實機收訊、真手機觸控手感、
  外部服務的簽章網址）。程式驗不到的就明說，不要讓綠燈暗示「全部都好了」。
